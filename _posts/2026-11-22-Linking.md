## 링킹이란?

C 프로그램은 보통 여러 개의 소스 파일로 나뉘어 있다. `main.c`에서 `sum.c`에 있는 `sum()`을 호출하는 경우를 생각해보자.

```c
// main.c
int sum(int *a, int n);

int array[2] = {1, 2};

int main()
{
    int val = sum(array, 2);
    return val;
}
```

```c
// sum.c
int sum(int *a, int n)
{
    int i, s = 0;

    for (i = 0; i < n; i++) {
        s += a[i];
    }
    return s;
}
```

caller는 calling convention 덕분에 함수의 내용을 몰라도 데이터를 어떻게 넘길지는 안다. 하지만 **제어를 어디로 넘길지**(`sum`이 어디에 있는지)는 모른다. 이걸 연결해주는 게 **링커(linker)** 다.

```bash
$ gcc -Og -o prog main.c sum.c
$ ./prog
```

이 한 줄 안에서 실제로는 다음 과정이 일어난다.

```
main.c ─(cpp, cc1, as)─▶ main.o ─┐
                                 ├─▶ Linker (ld) ─▶ prog
sum.c  ─(cpp, cc1, as)─▶ sum.o  ─┘
```

| 도구 | 하는 일 |
|---|---|
| cpp | 전처리 (`#include`, `#define` 처리) |
| cc1 | C → 어셈블리어 번역 (좁은 의미의 컴파일러) |
| as | 어셈블리어 → 기계어, relocatable object file(`.o`) 생성 |
| ld | 여러 `.o`를 합쳐 실행 파일 생성 |

각 소스 파일은 **따로따로** 번역된다. 링커는 어셈블리어가 아니라 **어셈블러가 만든 `.o` 파일들**을 입력으로 받는다.

## 링커를 쓰는 이유

**1. Modularity**
- 프로그램을 하나의 거대한 파일이 아니라 작은 소스 파일들의 모음으로 작성할 수 있다.
- 자주 쓰는 함수들을 라이브러리로 묶을 수 있다 (math library, standard C library).

**2. Efficiency**
- **시간:** 분리 컴파일(separate compilation). 파일 하나를 고치면 그 파일만 다시 컴파일하고 다시 링크하면 된다. 다른 파일은 건드리지 않아도 된다.
- **공간:** 라이브러리에 함수를 모아두더라도, 실행 파일에는 실제로 쓰는 함수의 코드만 들어간다.

## 링커가 하는 일

**Step 1: Symbol resolution**
- 프로그램은 심볼(전역변수, 함수)을 **정의**하고 **참조**한다.
- 심볼의 정의는 object 파일의 **symbol table**에 저장된다. 각 항목에는 이름, 크기, 위치가 들어 있다.
- 링커는 각 심볼 참조를 **정확히 하나의** 심볼 정의에 연결한다.

**Step 2: Relocation**
- 각 `.o`의 code, data 섹션을 하나로 합친다.
- `.o` 안의 상대 위치를 실행 파일의 최종 절대 주소로 바꾼다.
- 그 심볼을 참조하는 모든 곳을 새 주소로 고쳐 쓴다.

## Object 파일의 세 종류

| 종류 | 확장자 | 설명 |
|---|---|---|
| Relocatable object file | `.o` | 다른 `.o`와 합쳐서 실행 파일을 만들 수 있는 상태. 소스 파일 하나당 `.o` 하나 |
| Executable object file | `a.out` | 메모리에 그대로 복사해서 실행할 수 있는 상태 |
| Shared object file | `.so` | 로드할 때 또는 실행 중에 동적으로 링크되는 특별한 relocatable object file. 윈도우의 DLL |

`.so`를 쓰면 실행 파일에는 라이브러리 코드를 넣지 않고, 실행할 때 `.so` 파일 하나를 여러 프로그램이 함께 쓴다.

## ELF (Executable and Linkable Format)

리눅스에서 object 파일의 표준 바이너리 형식이다. 위의 세 종류 모두 같은 ELF 형식을 사용한다.

```
0 ┌──────────────────────┐
  │ ELF header           │  word size, byte ordering, 파일 종류, 머신 종류
  ├──────────────────────┤
  │ Segment header table │  메모리에 어떻게 올릴지 (실행 파일에만 필요)
  ├──────────────────────┤
  │ .text                │  코드
  │ .rodata              │  읽기 전용 데이터 (jump table 등)
  │ .data                │  초기화된 전역변수
  │ .bss                 │  초기화 안 된 전역변수
  │ .symtab              │  심볼 테이블
  │ .rel.text            │  .text의 relocation 정보
  │ .rel.data            │  .data의 relocation 정보
  │ .debug               │  디버깅 정보 (gcc -g)
  ├──────────────────────┤
  │ Section header table │  각 섹션의 오프셋과 크기 (섹션들의 목차)
  └──────────────────────┘
```

> `.bss`는 section header는 있지만 파일 안에서 공간을 차지하지 않는다. 저장할 초기값이 없으니 크기 정보만 남기고, 실제 공간은 실행할 때 메모리에 잡힌다.
{: .prompt-info }

## Linker Symbols

| 종류 | 설명 | 예 |
|---|---|---|
| Global symbols | 모듈이 정의하고 다른 모듈도 참조할 수 있는 심볼 (내보내는 심볼) | static이 아닌 함수, static이 아닌 전역변수 |
| External symbols | 모듈이 참조하지만 다른 모듈에 정의된 global 심볼 (가져오는 심볼) | `main.c` 입장에서의 `sum` |
| Local symbols | 모듈 안에서만 정의되고 쓰이는 심볼 | `static` 함수, `static` 전역변수 |

세 종류 모두 `.symtab`에 들어간다.

**local symbol은 다른 곳에서 안 쓰는데 왜 symtab에 들어갈까?**
local symbol도 `.data`, `.bss`, `.text`에 **실제 메모리 공간을 가지고 있기 때문**이다. 링커가 섹션을 합치면서 주소를 정해줘야 하므로 이름과 위치를 알아야 한다.

> **Local linker symbols are not local program variables!**
> 함수 안의 일반 지역변수(`val`, `i`, `s`)는 실행 중에 스택에 잡히므로 링커는 전혀 모른다.
{: .prompt-warning }

```c
static int count = 0;      // local symbol (.data)
int total = 0;             // global symbol

static void reset() {      // local symbol (.text)
    count = 0;
}

void add(int n) {          // global symbol
    static int calls = 0;  // local symbol (.data)
    int tmp = n * 2;       // 심볼 아님 (스택)
    calls++;
    count += tmp;
    total += tmp;
}
```

함수 안의 `static` 변수는 함수가 끝나도 값이 남아 있어야 하므로 스택이 아니라 `.data`나 `.bss`에 들어간다. 서로 다른 함수에 같은 이름의 static 변수가 있으면 컴파일러가 `x.1`, `x.2`처럼 고유한 이름의 local symbol로 만든다.

## Step 1: Symbol Resolution

`main.c`와 `sum.c` 예시에서 심볼을 분류하면 다음과 같다.

| | main.o | sum.o |
|---|---|---|
| `main` | Global | – |
| `array` | Global | – |
| `sum` | External | Global |
| `val`, `i`, `s` | 심볼 아님 | 심볼 아님 |

`sum`의 정의가 있는 `sum.o`에도 심볼이 반드시 있어야 한다. symbol table에는 참조뿐 아니라 **정의도 기록**되기 때문이다. 링커는 `main.o`의 "`sum`이 필요하다"와 `sum.o`의 "`sum`은 여기 있다"를 짝지어준다.

정리하면 **모든 참조는 정확히 하나의 정의에 연결되어야 한다.** 정의가 없으면 `undefined reference` 에러가 나고, 반대로 정의는 아무도 참조하지 않아도 괜찮다.

### Strong / Weak Symbols

같은 이름의 심볼이 여러 파일에 정의되어 있을 때를 위한 규칙이다.

- **Strong:** 함수, 초기화된 전역변수
- **Weak:** 초기화 안 된 전역변수

```c
// p1.c
int foo = 5;   // strong
p1() {}        // strong
```

```c
// p2.c
int foo;       // weak
p2() {}        // strong
```

**Linker's Symbol Rules**

- **Rule 1:** strong symbol이 여러 개면 안 된다 → 링크 에러
- **Rule 2:** strong 하나와 weak 여러 개가 있으면 → strong을 선택
- **Rule 3:** weak만 여러 개 있으면 → 아무거나 하나 선택 (`gcc -fno-common`으로 바꿀 수 있음)

### Linker Puzzles

아래 예시에서 박스 하나는 **소스 파일 하나**다. 두 파일을 따로 컴파일한 뒤 링크하는 상황이다.

| 파일 1 | 파일 2 | 결과 |
|---|---|---|
| `int x;` `p1() {}` | `p1() {}` | 링크 에러: strong symbol `p1`이 두 개 (Rule 1) |
| `int x;` `p1() {}` | `int x;` `p2() {}` | 두 `x`는 같은 변수를 가리킨다 (Rule 3). 의도한 게 맞을까? |
| `int x;` `int y;` `p1() {}` | `double x;` `p2() {}` | p2에서 `x`에 쓰면 `y`를 덮어쓸 **수도** 있다 |
| `int x=7;` `int y=5;` `p1() {}` | `double x;` `p2() {}` | p2에서 `x`에 쓰면 `y`를 덮어쓴다 (Rule 2) |
| `int x=7;` `p1() {}` | `int x;` `p2() {}` | 두 `x`는 초기화된 같은 변수를 가리킨다 |

세 번째, 네 번째 예시가 위험한 이유는 **링커가 이름만 보고 타입은 보지 않기 때문**이다. 링커는 `x`를 하나만 만들지만, p2.c의 기계어에는 이미 "`x` 주소에 8바이트를 쓴다"는 명령이 들어 있다. 4바이트짜리 int `x`가 선택되면 그 뒤에 있던 `y`까지 덮어쓰게 된다.

- 세 번째: 둘 다 weak라 어느 쪽이 선택될지 모르고, `y`가 `x` 바로 뒤에 있다는 보장도 없다 → "might"
- 네 번째: `int x=7`이 strong이라 반드시 4바이트 int가 선택된다 → "will"

### Global Variables 사용 지침

- 가능하면 전역변수를 쓰지 않는다.
- 써야 한다면
  - 가능하면 `static`을 붙인다 → local symbol이 되어 다른 파일과 섞이지 않는다.
  - 전역변수를 정의할 때는 초기화한다 → strong이 되어 중복 정의가 링크 에러로 드러난다.
  - 다른 파일의 전역변수를 참조할 때는 `extern`을 쓴다.

## Step 2: Relocation

### 섹션 합치기

각 `.o`의 `.text`끼리, `.data`끼리 합쳐서 실행 파일의 섹션 하나로 만든다.

```
main.o: .text [main()]   .data [int array[2]={1,2}]
sum.o : .text [sum()]
              │
              ▼
prog  : .text [system code | main() | sum() | more system code]
        .data [system data | int array[2]={1,2}]
```

### Relocation Entries

`main.c`를 번역할 때는 `array`와 `sum`의 최종 주소를 모른다. 그래서 그 자리를 **0으로 비워두고**, 나중에 어디를 어떻게 고칠지를 **relocation entry**로 남겨둔다.

```
$ objdump -r -d main.o

0000000000000000 <main>:
   0:   48 83 ec 08             sub    $0x8,%rsp
   4:   be 02 00 00 00          mov    $0x2,%esi
   9:   bf 00 00 00 00          mov    $0x0,%edi       # %edi = &array
                        a: R_X86_64_32 array           # Relocation entry
   e:   e8 00 00 00 00          callq  13 <main+0x13>  # sum()
                        f: R_X86_64_PC32 sum-0x4       # Relocation entry
  13:   48 83 c4 08             add    $0x8,%rsp
  17:   c3                      retq
```

- `a: R_X86_64_32 array` → 위치 `a`에 `array`의 **절대 주소**를 채워라
- `f: R_X86_64_PC32 sum-0x4` → 위치 `f`에 `sum`까지의 **PC 기준 상대 거리**를 채워라

### Relocated .text

링크 후 실행 파일을 보면 비워뒀던 자리가 채워져 있다.

```
$ objdump -dx prog

00000000004004d0 <main>:
  4004d0:  48 83 ec 08      sub    $0x8,%rsp
  4004d4:  be 02 00 00 00   mov    $0x2,%esi
  4004d9:  bf 18 10 60 00   mov    $0x601018,%edi  # %edi = &array
  4004de:  e8 05 00 00 00   callq  4004e8 <sum>    # sum()
  4004e3:  48 83 c4 08      add    $0x8,%rsp
  4004e7:  c3               retq

00000000004004e8 <sum>:
  ...
```

- `array` 자리 → 절대 주소 `0x601018`
- `sum` 자리 → 주소가 아니라 거리 `0x5`

```
0x4004e8 (sum) = 0x4004e3 (다음 명령어 주소) + 0x5
```

CPU는 call을 실행할 때 다음 명령어 주소에 이 값을 더해서 `sum`으로 점프한다.

> 정리: object 파일에는 실제 주소 값을 저장하지 않고 **relocation 정보**를 남긴다. 링커는 섹션을 합쳐 주소가 정해지면 그 정보를 보고 빈자리를 고쳐 쓴다.
{: .prompt-tip }

## Loading Executable Object Files

실행 파일의 섹션들은 실행될 때 메모리 세그먼트로 로드된다.

| 실행 파일 | 메모리 |
|---|---|
| `.init`, `.text`, `.rodata` | Read-only code segment |
| `.data`, `.bss` | Read/write data segment |
| (없음) | Run-time heap (`malloc`으로 생성) |
| (없음) | User stack (실행 중에 생성) |

힙과 스택은 실행 파일 안에 없고 실행 중에 만들어진다.

## Packaging Commonly Used Functions

`printf`, `scanf` 같은 자주 쓰는 함수들을 어떻게 제공할까?

- **Option 1:** 모든 함수를 소스 파일 하나에 넣는다 → 안 쓰는 함수까지 통째로 링크되므로 시간과 공간이 비효율적이다.
- **Option 2:** 함수마다 소스 파일을 따로 만든다 → 효율적이지만 프로그래머가 필요한 `.o`를 하나하나 직접 링크해야 해서 번거롭다.

## Static Libraries (.a)

두 방법의 장점을 합친 방식이다.

- 관련된 `.o` 파일 여러 개를 파일 하나로 묶고 인덱스를 붙인다 (**archive**, 확장자 `.a`).
- 링커는 해결되지 않은 참조가 있으면 archive 안에서 심볼을 찾는다.
- 참조를 해결해주는 **멤버 `.o`만** 실행 파일에 넣는다.

### Creating Static Libraries

```bash
unix> ar rs libc.a atoi.o printf.o … random.o
```

archiver(`ar`)로 `.o`들을 묶는다. 함수 하나를 고치면 그 파일만 다시 컴파일해서 archive 안의 해당 `.o`만 교체하면 된다 (incremental update).

### Commonly Used Libraries

| 라이브러리 | 크기 | 내용 |
|---|---|---|
| `libc.a` (C standard library) | 4.6MB, `.o` 1496개 | I/O, 메모리 할당, 시그널, 문자열, 날짜·시간, 난수, 정수 연산 |
| `libm.a` (C math library) | 2MB, `.o` 444개 | 실수 연산 (sin, cos, tan, log, exp, sqrt …) |

`ar -t libc.a`로 보면 `fork.o`, `fprintf.o`처럼 함수별 `.o`가 따로 들어 있다. 그래서 필요한 `.o`만 골라서 링크할 수 있다.

### Linking with Static Libraries

```c
// main2.c
#include <stdio.h>
#include "vector.h"

int x[2] = {1, 2};
int y[2] = {3, 4};
int z[2];

int main()
{
    addvec(x, y, z, 2);
    printf("z = [%d %d]\n", z[0], z[1]);
    return 0;
}
```

`addvec.c`, `multvec.c`를 `ar`로 묶어 `libvector.a`를 만들고 링크하면, 실행 파일 `prog2c`에는 다음만 들어간다.

- `main2.o`
- `libvector.a`의 `addvec.o`
- `libc.a`의 `printf.o`와 `printf`가 부르는 모듈들

`multvec.o`는 아무도 참조하지 않으므로 들어가지 않는다. (`prog2c`의 c는 compile-time)

### Using Static Libraries

링커가 external reference를 해결하는 방식은 다음과 같다.

1. 명령줄 **순서대로** `.o`와 `.a` 파일을 scan한다.
2. scan하는 동안 **해결되지 않은 참조 목록**을 유지한다.
3. 새 파일을 만날 때마다 목록의 참조를 그 파일에 정의된 심볼로 해결한다.
4. scan이 끝났는데 목록에 남은 참조가 있으면 에러다.

```bash
unix> gcc -L. libtest.o -lmine    # 성공
unix> gcc -L. -lmine libtest.o    # 실패
libtest.o: In function `main':
libtest.o(.text+0x4): undefined reference to `libfun'
```

두 번째 명령에서는 `libmine.a`를 지나갈 때 아직 `libfun`이 필요하다는 걸 모르므로 아무것도 가져오지 않는다. 그 뒤 `libtest.o`에서 `libfun`이 필요해지지만, 링커는 지나간 파일로 되돌아가지 않는다.

> **명령줄 순서가 중요하다. 라이브러리는 명령줄 맨 뒤에 둔다.**
{: .prompt-warning }

## Shared Libraries (.so)

Static library의 단점은 다음과 같다.

- 저장된 실행 파일마다 같은 코드가 중복된다 (모든 프로그램이 libc를 쓴다).
- 실행 중인 프로그램마다 메모리에도 중복된다.
- 시스템 라이브러리의 버그를 고치면 모든 프로그램을 다시 링크해야 한다.

해결책이 **shared library**다. 코드와 데이터를 **load-time 또는 run-time에 동적으로** 로드하고 링크한다. dynamic link library, `.dll`, `.so`라고도 부른다.

- **Load-time linking:** 실행 파일이 처음 로드되고 실행될 때 일어난다. 리눅스에서는 일반적인 경우로, dynamic linker(`ld-linux.so`)가 자동으로 처리한다. 표준 C 라이브러리 `libc.so`는 보통 동적으로 링크된다.
- **Run-time linking:** 프로그램이 시작된 뒤에 일어난다. 리눅스에서는 `dlopen()` 인터페이스를 쓴다. 소프트웨어 배포, 고성능 웹 서버, runtime library interpositioning 등에 활용된다.
- shared library의 코드는 여러 프로세스가 공유할 수 있다.

### Dynamic Linking at Load-time

```bash
unix> gcc -shared -o libvector.so addvec.c multvec.c
```

```
main2.o + libc.so, libvector.so (relocation, symbol table 정보만)
        │ Linker (ld)
      prog2l   ← partially linked executable
        │ Loader (execve)
        │ + libc.so, libvector.so (코드와 데이터)
  Dynamic linker (ld-linux.so)
        │
  fully linked executable in memory
```

`ld` 단계에서는 `.so`의 코드를 복사하지 않고 정보만 기록한다. 실제 코드는 로드할 때 dynamic linker가 연결한다. (`prog2l`의 l은 load-time)

### Dynamic Linking at Run-time

```c
#include <stdio.h>
#include <stdlib.h>
#include <dlfcn.h>

int x[2] = {1, 2};
int y[2] = {3, 4};
int z[2];

int main()
{
    void *handle;
    void (*addvec)(int *, int *, int *, int);
    char *error;

    /* addvec()이 들어 있는 shared library를 동적으로 로드 */
    handle = dlopen("./libvector.so", RTLD_LAZY);
    if (!handle) {
        fprintf(stderr, "%s\n", dlerror());
        exit(1);
    }

    /* 방금 로드한 addvec() 함수의 포인터를 얻음 */
    addvec = dlsym(handle, "addvec");
    if ((error = dlerror()) != NULL) {
        fprintf(stderr, "%s\n", error);
        exit(1);
    }

    /* 일반 함수처럼 호출 */
    addvec(x, y, z, 2);
    printf("z = [%d %d]\n", z[0], z[1]);

    /* shared library 언로드 */
    if (dlclose(handle) < 0) {
        fprintf(stderr, "%s\n", dlerror());
        exit(1);
    }
    return 0;
}
```

실행 중에 **이름(문자열)으로** 함수를 찾아서 쓴다.

## Linking Summary

- 링킹은 여러 object 파일로 프로그램을 만들 수 있게 해주는 기술이다.
- 링킹은 세 시점에 일어날 수 있다.
  - Compile time: 프로그램을 컴파일할 때
  - Load time: 프로그램을 메모리에 로드할 때
  - Run time: 프로그램이 실행되는 중에
- 링킹을 이해하면 이상한 에러를 피할 수 있다.

## Case Study: Library Interpositioning

임의의 함수 호출을 **가로채는(intercept)** 링킹 기법이다. compile time, link time, load/run time에 할 수 있다.

**활용 예**
- Security: confinement(sandboxing), 보이지 않는 암호화
- Debugging: Facebook 엔지니어들이 iPhone 앱의 1년 묵은 버그를 write 계열 함수 호출을 가로채서 찾아냄
- Monitoring / Profiling: 함수 호출 횟수 세기, malloc tracing(메모리 누수 탐지, 주소 추적)

**예제 목표:** 아래 프로그램의 소스를 수정하지 않고 `malloc`/`free`의 주소와 크기를 추적한다.

```c
// int.c
#include <stdio.h>
#include <malloc.h>

int main()
{
    int *p = malloc(32);
    free(p);
    return(0);
}
```

세 방법 모두 `mymalloc.c` 하나에 `#ifdef`로 버전을 나눠두고, `-D` 옵션으로 골라서 컴파일한다.

### Compile-time Interpositioning

```c
// mymalloc.c
#ifdef COMPILETIME
#include <stdio.h>
#include <malloc.h>

/* malloc wrapper function */
void *mymalloc(size_t size)
{
    void *ptr = malloc(size);
    printf("malloc(%d)=%p\n", (int)size, ptr);
    return ptr;
}

/* free wrapper function */
void myfree(void *ptr)
{
    free(ptr);
    printf("free(%p)\n", ptr);
}
#endif
```

```c
// malloc.h (직접 만든 헤더)
#define malloc(size) mymalloc(size)
#define free(ptr) myfree(ptr)

void *mymalloc(size_t size);
void myfree(void *ptr);
```

```bash
linux> make intc
gcc -Wall -DCOMPILETIME -c mymalloc.c
gcc -Wall -I. -o intc int.c mymalloc.o
linux> make runc
./intc
malloc(32)=0x1edc010
free(0x1edc010)
```

`int.c`가 현재 폴더(`-I.`)의 `malloc.h`를 include하므로, 전처리 단계에서 `malloc`, `free` 호출이 매크로에 의해 `mymalloc`, `myfree`로 바뀐다.

### Link-time Interpositioning

```c
// mymalloc.c
#ifdef LINKTIME
#include <stdio.h>

void *__real_malloc(size_t size);
void __real_free(void *ptr);

/* malloc wrapper function */
void *__wrap_malloc(size_t size)
{
    void *ptr = __real_malloc(size); /* Call libc malloc */
    printf("malloc(%d) = %p\n", (int)size, ptr);
    return ptr;
}

/* free wrapper function */
void __wrap_free(void *ptr)
{
    __real_free(ptr); /* Call libc free */
    printf("free(%p)\n", ptr);
}
#endif
```

```bash
linux> make intl
gcc -Wall -DLINKTIME -c mymalloc.c
gcc -Wall -c int.c
gcc -Wall -Wl,--wrap,malloc -Wl,--wrap,free -o intl int.o mymalloc.o
linux> make runl
./intl
malloc(32) = 0x1aa0010
free(0x1aa0010)
```

- `-Wl`: 뒤의 인자를 링커에 전달한다 (콤마는 공백으로 바뀐다).
- `--wrap,malloc`: 링커가 참조를 특별한 방식으로 resolve하게 한다.
  - `malloc` 참조 → `__wrap_malloc`으로
  - `__real_malloc` 참조 → `malloc`으로

즉 **symbol resolution 단계를 바꾸는 트릭**이다.

### Load/Run-time Interpositioning

```c
// mymalloc.c
#ifdef RUNTIME
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <dlfcn.h>

/* malloc wrapper function */
void *malloc(size_t size)
{
    void *(*mallocp)(size_t size);
    char *error;

    mallocp = dlsym(RTLD_NEXT, "malloc"); /* Get addr of libc malloc */
    if ((error = dlerror()) != NULL) {
        fputs(error, stderr);
        exit(1);
    }
    char *ptr = mallocp(size); /* Call libc malloc */
    fprintf(stderr, "malloc(%d) = %p\n", (int)size, ptr);
    return ptr;
}

/* free wrapper function */
void free(void *ptr)
{
    void (*freep)(void *) = NULL;
    char *error;

    if (!ptr)
        return;

    freep = dlsym(RTLD_NEXT, "free"); /* Get address of libc free */
    if ((error = dlerror()) != NULL) {
        fputs(error, stderr);
        exit(1);
    }
    freep(ptr); /* Call libc free */
    fprintf(stderr, "free(%p)\n", ptr);
}
#endif
```

```bash
linux> make intr
gcc -Wall -DRUNTIME -shared -fpic -o mymalloc.so mymalloc.c -ldl
gcc -Wall -o intr int.c
linux> make runr
(LD_PRELOAD="./mymalloc.so" ./intr)
malloc(32) = 0xe60010
free(0xe60010)
```

`LD_PRELOAD` 환경변수는 dynamic linker가 해결되지 않은 참조(예: `malloc`)를 **`mymalloc.so`에서 먼저** 찾게 한다. wrapper 안에서는 `dlsym(RTLD_NEXT, "malloc")`으로 그다음 순서에 있는 libc의 진짜 `malloc` 주소를 얻어서 호출한다.

### Interpositioning Recap

| 시점 | 방법 |
|---|---|
| Compile time | `malloc`/`free` 호출이 매크로로 `mymalloc`/`myfree` 호출로 확장된다 |
| Link time | 링커 트릭으로 이름 해석을 바꾼다: `malloc` → `__wrap_malloc`, `__real_malloc` → `malloc` |
| Load/Run time | 같은 이름의 `malloc`/`free`를 직접 구현하고, 동적 링킹으로 라이브러리의 진짜 `malloc`/`free`를 다른 이름으로 불러온다 |
